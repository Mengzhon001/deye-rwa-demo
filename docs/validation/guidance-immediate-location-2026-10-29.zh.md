# 操作定位与业务状态刷新分离

用户点击中介机构的“定位操作”后，原实现会先调用完整的 `/api/state`，等待产品、账户、认购、余额和估值等信息返回，再打开相关页面。这使一次页面定位承担了工作台全量读取的延迟。此前的 RPC 聚合优化缩短了读取时间，但没有消除这次不必要的等待。

本次修改让定位直接使用页面已经加载的业务状态。引导面板显示该份数据的读取时间，并提供独立的“刷新业务状态”按钮。条件说明中的“重新定位”只负责重新打开页面和寻找控件。其他参与者完成操作后，用户可以刷新业务状态，查看最新结果。提交业务操作仍经过后端交易准备和合约条件检查，本次没有放宽审批、募集金额或现金留存要求。

已在公网统一入口通过隐藏浏览器验证两条链的投资者定位，以及 Base Sepolia 中介机构的结算定位。条件不足时，结算控件保持禁用，弹窗标出缺项，并提供认购订单审核等具体入口。测试中的资格和认购状态只在浏览器响应中构造，没有写回后端。

六组浏览器检查覆盖了中英文、桌面与手机、重复定位、脚本和样式加载失败后的重试、状态查询失败后的恢复，以及状态请求尚未返回时继续定位。测试确认定位本身没有新增 `/api/state` 请求，普通页面导航也没有把旧数据的读取时间改成新时间。查询返回后会重新核对高亮的 DOM，不会恢复已经关闭的查询弹窗。

测试还发现，手机端在导览首次绘制完成前快速关闭时，Driver.js 可能没有调用完成清理回调，导致自定义的面板隐藏样式残留。关闭入口现在主动清理高亮并恢复焦点，重复定位检查已通过。

本次浏览器受控测试中，正常投资资格定位约为 117 和 121 毫秒，条件不足的结算定位约为 91 和 102 毫秒。另使用已有隔离账户和真实 Rabby 0.94.11，在 Base Sepolia 实际页面上验证了现金流时间轴、认购金额和认购按钮的三个提示，首次定位为 839 毫秒。这些是单次现场采样，不是延迟保证，也不代表业务状态查询或交易确认同样快速。

29 项现有引导规则检查和网关回归检查通过。此次没有重置产品、推进财务时间或提交公链业务交易，也没有重新运行完整生命周期。原始截图和结果保存在本机 `.data/unified-app/validation/guidance-resources/`，不包含钱包密钥。

可重复执行的浏览器检查入口为 `scripts/test-unified-guidance.mjs` 和 `scripts/test-unified-guidance-rabby.mjs`。前者使用真实签名会话与只读的浏览器响应场景，后者使用已有隔离的真实 Rabby 配置；两者均以隐藏浏览器运行，并要求显式指定本机测试配置路径。
