# Base Sepolia 工作台读取性能核对

本次核对针对业主签名登录后停留在工作台加载页的现象。后端仍使用 `https://sepolia.base.org`，没有更换 RPC 服务商。现场探测中，`eth_chainId` 和 `eth_blockNumber` 分别用了约 310 毫秒和 291 毫秒，均成功返回。该结果不能说明所有 RPC 请求都同样快速，但说明当时节点可以访问，不能把整页等待直接等同于链停机。

检查发现，工作台会读取产品条款、多个账户、认购、分配和历史事件。原实现需要多轮独立查询，还重复读取了同一份产品列表。底层 HTTP 库默认允许单个请求等待五分钟，遇到没有响应的请求时，会进一步阻塞串行读取队列。

本次修改合并了基础合约读取、多个账户及可领取分配的读取，并通过 Multicall3 查询多个地址的原生币余额。产品大厅和产品选项复用一次列表查询。单个 RPC HTTP 请求最多等待十秒，HTTP 限流不再触发底层隐式重试。原有只读 JSON-RPC 限流重试仍有次数限制，交易广播不会由该读取封装重复发送。浏览器的四十五秒加载超时和保留登录后的重试入口继续生效。

| 检查对象 | 本次测得的耗时 |
| --- | --- |
| 修改前的业主工作台 | 15.840 秒、11.160 秒 |
| 修改后的业主工作台 | 12.657 秒、8.141 秒 |
| 修改后的投资者工作台 | 7.599 秒、9.384 秒 |
| 真实 Rabby 业主登录及刷新 | 9.830 秒、8.261 秒 |

这些是同一公网入口的少量顺序采样，不是服务时延保证。更新后的第一次读取仍可能包含历史记录核对，公共 RPC 的响应也会波动。本次没有确认当前存在 RPC 限流故障，后续如接入专用 RPC，应继续复测同一组查询，而不能只按节点名称判断速度。

更新前后，合约地址、产品阶段、资产池现金、认购总额、份额总量，以及四个账户的余额、资格、认购记录和领取记录完全一致。这里只比较了读取结果，没有代用户提交公链业务交易。

七项 RPC 与聚合读取检查、三十八项业务界面规则检查和 TypeScript 检查均通过。另在一次性 Hardhat 链上运行了原有四角色回归，覆盖九个月回款、分配和领取、原子转让、部分赎回、独立受托审批、重启、重新估值及重置恢复。真实 Rabby 测试则使用公网 Base Sepolia 的业主账户完成登录和刷新，并成功进入工作台。更新只重新启动了 Base Sepolia 的应用容器，继续使用原有持久化业务数据和合约。
